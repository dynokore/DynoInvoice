# svc-access

access-svc (INV-MOD-64): who may do what, on whose authority. Grants (role, scope, validity window), live authorisation,
the AuthorityChanged feed of every service's authority replica, and the token verification material of the gateway.

**Status:** Wave 2 skeleton (INV-T-4934). Follows the design in
[invoice-docs](http://registry.example.internal/invoice/invoice-docs); change the design there first, then the code here.

## Modules (TPL-01, ARC-10)

| Module | Holds |
| --- | --- |
| `access-contract` | server interfaces and DTOs generated by `gst.contract-server` from `platform-contracts/access` (the pinned bundle); the contract documents as resources |
| `access-domain` | pure Kotlin: roles, scopes, grants, the authorisation policy, the permission matrix, revocation entries (a `java.sql` type may be named; Spring, jOOQ and Jackson may not) |
| `access-application` | use cases and ports: `Authorise`, `GrantRoleUseCase`, `RevokeGrantUseCase`, `GrantConsentUseCase`, `WithdrawConsentUseCase`, `AgentScope`, `RevocationList`, `VerificationKeys` |
| `access-adapters` | HTTP controllers, jOOQ repositories, the outbox mappers, the Flyway migrations (`db/migration`) |
| `access-bootstrap` | the Spring Boot application (TPL-18), `application.yaml` (TPL-16), the acceptance and architecture tests |

## Repository gates (`./gradlew check`)

- **`acKeyCoverage`** (root, `gradle/gates/ac-key-coverage.gradle.kts`): `ac-keys.tsv` lists the acceptance criteria
  of this service's tasks (criterion, task, wave). Fails when the table is missing, empty or malformed, when a wave-2 row
  has no test whose name contains its key as a whole token, or when a test name holds a key that is in no row.
  Every later task of this service appends the rows of its own `ac_refs` and deferred criteria.
- **`operations.tsv`** (`OperationsTableTest`): every operationId and channel of the contract with the task that
  implements it and its state (`open`, `done`). Fails when the contract holds one the table lacks, or a row the contract
  does not hold, or when a `done` operation still answers 501.
- **Architecture** (`ArchitectureTest`): the layer rule, jOOQ-only database access, the SQL guards and the migration lint.

## Dependency locking and verification (STK-72)

Every resolvable configuration of every project is locked in strict mode (`gradle.lockfile` per module,
`buildscript-gradle.lockfile`, `gradle/settings-gradle.lockfile`) and every downloaded artefact is verified against
`gradle/verification-metadata.xml` (checksums and signatures, key servers off). No build file or CI job turns
verification off. When a dependency or plugin changes, use an empty Gradle user home and write the locks and the metadata
in one pass:

```sh
./gradlew resolveAndLockAll compileKotlin compileTestKotlin spotlessCheck checkDependencyCatalogUsage verifyBannedDependencies \
  -x test --continue --write-locks --write-verification-metadata sha256,pgp --export-keys --no-configuration-cache
```

## Identity provider, group mapping and break-glass (INV-T-4938)

- `access.identity-provider.issuer-uri` (required, env `ACCESS_IDP_ISSUER_URI`) is the issuer of the `IdentityProvider`
  binding; service-runtime builds the `EndUserPrincipalResolver` from it. No class of this repository implements the port.
- `access.identity-provider.directory.{base-uri,realm,client-id,client-secret-ref}` (all required, no default, env
  `ACCESS_IDP_DIRECTORY_*`) say where directory groups are read: the Keycloak Admin REST API of the realm, with the
  client-credentials token of the read-only client `access-svc-directory-reader`. `client-secret-ref` is a SecretStore
  reference. A customer directory that is not Keycloak is federated or brokered into Keycloak (INV-Q-8835 A).
- `access.idp-group-sync.interval` (required, ISO-8601, `PT15M` in `application.yaml`) is the interval of the directory-group
  synchronisation (owner item INV-Q-8667). There is no default in code. The scheduler finds the tenants through
  `access.claim_idp_sync_tenants()` (a `SECURITY DEFINER` function owned by `access_sys`, executable by `access_runtime`
  only) and binds each tenant before it runs the use case.
- `mapIdpGroup`, `unmapIdpGroup`, `unlockBreakGlass` and `recordBreakGlassAction` are built. ACC-002 travels as the
  platform event `BreakGlassAlertRaised`; `AccessAlertRaised` stays the entity-scoped event of ACC-001, ACC-003 and
  ACC-004 (its publisher is `AccessAlertOutbox`, wired by INV-T-4941). `signInBreakGlass` and `resealBreakGlass` are
  INV-T-8853.
- The simulator image of the tests is named by digest in `access-bootstrap/src/test/resources/simulators.properties`.

## Open items

- INV-AC-1912 (entity-scope row policy) is deferred to INV-T-7520 (INV-Q-7453 option B): its row in `ac-keys.tsv` carries
  wave 3 and no test here carries the key; this service asserts only the tenant-level part (unbound session sees zero rows).
- The action catalogue and the scope grammar are unpublished: until INV-T-4935 lands the production permission matrix is
  empty and every authorisation answers DENY.
- Agent consent (INV-T-4939): `grantConsent` and `withdrawConsent` are implemented. A grant of `agent.operator` is usable by
  `authorise` only while the consent record of the client entity, read at that moment, grants the scope item the
  permission needs. The permission-to-item table (`ScopeItemRequirements`) is empty in production, so an agent is refused
  until the owner rules it (merge request, "Gaps"). The document-list port of the handover statement is unbound until
  Wave 3 and the statement then names the list as unavailable (INV-Q-4900).
