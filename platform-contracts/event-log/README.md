# event-log

Topic definitions of the `event-log` component (SDS §18.14).

## Topics

`topics.yaml` is generated by `generate-topics.py` from every `*/asyncapi.yaml`
and never hand-edited; CI's `event-log-topics-drift-check` regenerates and
diffs it.

- `topics:` one event topic per event type, with its producers (relay
  `INSERT`) and subscribers (consumer `SELECT`) (INV-REQ-1205 b3).
- `replay_topics:` one replay topic per (producer, subscriber) pair of the
  event topics, `gst.<producer>.replay-<subscriber>.v1` (service names
  without `-svc`), derived, never hand-entered (coordinator ruling
  INV-Q-3601). A pair whose producer is `every service` (INV-Q-3539) gets
  `gst.platform.replay-<subscriber>.v1` with producers `[every service]`, the
  namespace its event topics share (INV-Q-3625). A replay topic carries the
  events the producer re-emits when it replays by scope or runs a full sync
  (INV-REQ-1205 b4), limited to the types that subscriber subscribes to from
  that producer, and ends each replay with a `ReplayCompleted` completion
  marker (INV-Q-3644). It is addressed by grant to one consumer: only that
  producer's relay inserts and only that subscriber selects, so a consumer
  never reads another consumer's replay. Like every topic it is purged by
  its `content_topic` marker: true when any type it carries is a content
  topic (content window), false otherwise (event-log retention).
- `replay_request_topics:` one request topic per consumer,
  `gst.<consumer>.replay-requested.v1`, carrying `ReplayRequested` (owner
  ruling INV-Q-3599). The consumer's relay inserts and every producer of a
  topic it subscribes to selects (`every service` counting as one value),
  so a producer reads the request under the consumer `SELECT` grant of
  INV-REQ-1205 b3.
- `record_topic` on every topic: true when the topic's message declares
  `x-record-topic: true` (today AuditEntryRecorded and DecisionTraceRecorded),
  false on every other topic, including replay and request topics. The purge
  never removes a record topic's rows above evidence-svc's recorded position
  (owner ruling INV-Q-3627).
- `retained_while_resolvable` on every topic (written after `record_topic`):
  true when the topic's message declares `x-retained-while-resolvable: true`
  (today RulePackStaged), absent meaning false. A replay topic is true exactly
  when any type it carries is (so the four replay topics that carry
  RulePackStaged); a request topic is false. The event log keeps such a topic
  for the pack artefact retention so a pack holder can refill its cache from
  it (INV-REQ-1210, INV-Q-6281). A message declaring both this marker and
  `x-invoice-content: true`, and a replay topic whose types make both true,
  fail the generator. The purge itself is outside this contract.

## Model check (INV-T-13621, INV-Q-9000 A; INV-T-16628, INV-Q-16624 D)

`check-model-subscribers.py <model-architecture-dir> <contracts-root>` compares
invoice-docs `events.yaml` and `services.yaml` with `topics.yaml`: every
consumer and producer of a model event must be a subscriber or producer of its
topic, every event with `feeds_runtime_replicas: true` must be subscribed by
every service except `console-web` and its producers, every topic's event type
has an event, and every event has a topic. The rules are strict.

**Address rule (INV-T-17778).** Every `topics.yaml` entry with a string `topic`
and a string `event_type` is checked in both modes, including the entries of
`EXEMPT_TOPICS` and `SUPERSEDED_TOPICS`; the rule has no exemption. The event
type must match `^com\.dynokore\.gst\.([a-z][a-z0-9]*)\.([A-Z][A-Za-z0-9]*)\.v([0-9]+)$`,
otherwise the finding is `topic <topic>: event type <event_type> is malformed`.
The expected address is `gst.<group 1>.<kebab>.v<group 3>`, where `<kebab>` is
group 2 with `-` inserted before every upper-case letter except the first,
lower-cased. The topic must equal it as a whole string (no strip, no case
folding, no prefix test), otherwise the finding is
`topic <topic>: address differs from the address derived from event type <event_type> (expected <expected>)`.

**Pinned mode.** The job `invoice-docs-checks` runs
`check-model-subscribers.py --pin event-log/model-pin.txt --docs-repo <invoice-docs clone> <contracts-root>`.
It reads the two model files at the pinned commit with
`git show <pin>:model/architecture/<file>` and applies the same rules. The pin
must be an ancestor of `origin/main` of the clone. A missing or malformed pin
file, an unreadable commit and a commit that is not an ancestor each fail with
one `model-pin:` line. Every pinned run prints
`model pin: <sha> (invoice-docs main <short sha>)`.

**Pin file.** `event-log/model-pin.txt` is exactly one line: 40 lowercase
hexadecimal characters and a newline, no comment, no whitespace. A merge
request that adds the topic of a new event type moves the pin to the
invoice-docs main commit that holds the model change.

**Head run.** The job `model-subscribers-head-check` runs only on the pipeline
schedule. It runs the unpinned invocation against the head of invoice-docs main
with no added exemption. It is red while a model change is ahead of its
contract; that is expected and tells the contract task to start.

**Order of work.** For a new event type: the model task first, the contract
task second (the contract task moves the pin). For a new consumer or producer
of an existing event: the contract task first, the model task second.

## Consumed-event producers (INV-T-14082, INV-Q-14079 A)

A service's `asyncapi.yaml` may declare, as a root key before `channels`, the
extension `x-consumed-events`: a sequence of entries with exactly the keys
`event_type`, `topic` and `producers` (a non-empty sequence of strings). It is
not a channel, so a catalogue that reads channels as produced events ignores
it. `generate-topics.py` checks every entry in both modes (`--write` and
`--check`) by string equality: `event_type` is the event type of a generated
topic, `topic` is that topic's address, the sorted `producers` equal the
topic's `producers`, and the declaring service (directory name plus `-svc`) is
one of the topic's `subscribers`. A failure exits non-zero and prints the
file, the event type and the topic. The key adds nothing to `topics.yaml`.
