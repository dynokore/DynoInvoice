# event-log

Topic definitions of the `event-log` component (SDS §18.14).

## Topics

`topics.yaml` is generated by `generate-topics.py` from every `*/asyncapi.yaml`
and never hand-edited; CI's `event-log-topics-drift-check` regenerates and
diffs it.

- `topics:` one event topic per event type, with its producers (relay
  `INSERT`) and subscribers (consumer `SELECT`) (INV-REQ-1205 b3).
- `replay_topics:` one replay topic per (producer, subscriber) pair of the
  event topics, `gst.<producer>.replay-<subscriber>.v1` (service names
  without `-svc`), derived, never hand-entered (coordinator ruling
  INV-Q-3601). A pair whose producer is `every service` (INV-Q-3539) gets
  `gst.platform.replay-<subscriber>.v1` with producers `[every service]`, the
  namespace its event topics share (INV-Q-3625). A replay topic carries the
  events the producer re-emits when it replays by scope or runs a full sync
  (INV-REQ-1205 b4), limited to the types that subscriber subscribes to from
  that producer, and ends each replay with a `ReplayCompleted` completion
  marker (INV-Q-3644). It is addressed by grant to one consumer: only that
  producer's relay inserts and only that subscriber selects, so a consumer
  never reads another consumer's replay. Like every topic it is purged by
  its `content_topic` marker: true when any type it carries is a content
  topic (content window), false otherwise (event-log retention).
- `replay_request_topics:` one request topic per consumer,
  `gst.<consumer>.replay-requested.v1`, carrying `ReplayRequested` (owner
  ruling INV-Q-3599). The consumer's relay inserts and every producer of a
  topic it subscribes to selects (`every service` counting as one value),
  so a producer reads the request under the consumer `SELECT` grant of
  INV-REQ-1205 b3.
- `record_topic` on every topic: true when the topic's message declares
  `x-record-topic: true` (today AuditEntryRecorded and DecisionTraceRecorded),
  false on every other topic, including replay and request topics. The purge
  never removes a record topic's rows above evidence-svc's recorded position
  (owner ruling INV-Q-3627).
- `retained_while_resolvable` on every topic (written after `record_topic`):
  true when the topic's message declares `x-retained-while-resolvable: true`
  (today RulePackStaged), absent meaning false. A replay topic is true exactly
  when any type it carries is (so the four replay topics that carry
  RulePackStaged); a request topic is false. The event log keeps such a topic
  for the pack artefact retention so a pack holder can refill its cache from
  it (INV-REQ-1210, INV-Q-6281). A message declaring both this marker and
  `x-invoice-content: true`, and a replay topic whose types make both true,
  fail the generator. The purge itself is outside this contract.

## Model check (INV-T-13621, INV-Q-9000 A)

`check-model-subscribers.py <model-architecture-dir> <contracts-root>` (job
`invoice-docs-checks`, run on merge requests and on main) compares invoice-docs
`events.yaml` and `services.yaml` with `topics.yaml`: every consumer and
producer of a model event must be a subscriber or producer of its topic, and
every event with `feeds_runtime_replicas: true` must be subscribed by every
service except `console-web` and its producers. Order of work: the check
accepts a contract that is ahead of the model and rejects a model that is
ahead of the contract, so for a new consumer or producer the contract task
merges first and the model task second.
